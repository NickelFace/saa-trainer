# Шифрование, KMS и секреты

Шифрование в AWS делится на две задачи: данные в покое (at rest) и данные в передаче
(in transit). Первую почти всегда закрывает KMS вместе с сервисом хранения, вторую —
TLS-сертификат от ACM плюс политика, запрещающая незашифрованные соединения.

## KMS: типы ключей

| Тип | Кто владеет | Ротация | Политика ключа | Видимость в CloudTrail |
|---|---|---|---|---|
| AWS owned | AWS, общий для сервиса | AWS | нет | нет |
| AWS managed (`aws/s3`) | ваш аккаунт, создаёт сервис | раз в год, автоматически | нельзя менять | да |
| Customer managed (CMK) | вы | включаемая, раз в год или по расписанию | ваша | да |
| Imported key material | вы | вручную, только повторный импорт | ваша | да |
| CloudHSM-backed / External store | вы | вручную | ваша | да |

Customer managed ключ выбирают, когда требуется своя политика доступа, аудит
использования, ротация под контролем, кросс-аккаунтный доступ или возможность быстро
отозвать доступ к данным. Формулировки «control over the key policy», «ability to
disable/delete the key», «audit key usage» указывают именно на него.

Удаление ключа возможно только через ожидание от 7 до 30 дней. Отключение ключа
мгновенно делает данные нечитаемыми — это ответ на «немедленно прекратить доступ
к зашифрованным данным».

## Как работает конвертное шифрование

1. Сервис запрашивает у KMS data key (`GenerateDataKey`).
2. KMS отдаёт открытый и зашифрованный варианты ключа.
3. Данные шифруются открытым ключом локально, он стирается из памяти.
4. Рядом с данными хранится зашифрованный ключ; при чтении он расшифровывается через
   `Decrypt`.

Отсюда следствия: KMS никогда не видит сами данные, размер прямого шифрования через
KMS ограничен 4 КБ, а нагрузка на KMS считается запросами. Массовые операции упираются
в квоты KMS — снижают их S3 Bucket Keys, кэш data key в AWS Encryption SDK и
`GenerateDataKeyWithoutPlaintext` для пакетной записи.

## Мультирегиональные ключи

Multi-Region keys — набор ключей с общим материалом в разных регионах. Нужны там, где
зашифрованные данные пересекают границу региона: CRR бакета с шифрованием, глобальные
таблицы DynamoDB, копирование снапшотов в регион аварийного восстановления. Обычный
CMK привязан к своему региону, и копия снапшота в другом регионе должна перешифровываться
локальным ключом — это обычно и есть правильный ответ в вопросах про DR.

## Шифрование по сервисам

- S3: SSE-S3 по умолчанию, SSE-KMS для контроля и аудита, SSE-C для собственных ключей,
  Bucket Keys для экономии; политика может запрещать незашифрованную запись.
- EBS: шифрование тома и снапшотов, ключ выбирается при создании; включить шифрование
  существующего незашифрованного тома напрямую нельзя — делают снапшот и восстанавливают
  его в зашифрованный том. Атрибут аккаунта «encryption by default» заставляет шифровать
  все новые тома.
- RDS и Aurora: шифрование включается при создании; чтобы зашифровать существующую базу,
  делают снапшот, копируют его с шифрованием и восстанавливают. Read replica наследует
  состояние шифрования источника.
- DynamoDB: шифрование включено всегда, выбирается только тип ключа.
- EFS и FSx: шифрование в покое при создании, в передаче — при монтировании (TLS).
- SQS, SNS, Kinesis, CloudWatch Logs: SSE-KMS включается на ресурсе.
- Redshift, EMR, OpenSearch, Glue: шифрование кластера и промежуточных данных
  настраивается при создании.

## ACM и трафик

ACM выпускает бесплатные публичные сертификаты и автоматически продлевает те, что
проверены через DNS. Сертификаты ACM нельзя экспортировать и поставить на собственный
сервер — для этого есть ACM Private CA. Сертификат для CloudFront всегда выпускается
или импортируется в us-east-1, для ALB и API Gateway — в регионе ресурса.

Сертификат от стороннего CA можно импортировать в ACM, но выпустить его цепочкой
от чужого CA сервис не может — на этом построена не одна ловушка.

## Secrets Manager и Parameter Store

| | Secrets Manager | SSM Parameter Store |
|---|---|---|
| Цена | за секрет и за вызов | стандартные параметры бесплатно |
| Ротация | встроенная, через Lambda | нет, только вручную |
| Кросс-аккаунт | resource policy | через RAM/политику, ограниченно |
| Репликация в регионы | да | нет |
| Интеграция с RDS/Redshift/DocumentDB | да, готовые ротаторы | нет |
| Размер | до 64 КБ | 4 КБ (advanced до 8 КБ) |

Если в требовании есть слова «автоматическая ротация», ответ — Secrets Manager. Если
акцент на «дёшево хранить конфигурацию и несекретные параметры», ответ — Parameter Store.
Хардкод учётных данных в коде, переменных окружения или AMI — всегда неверный вариант.

## Что спрашивают на экзамене

1. «Все новые EBS-тома должны быть зашифрованы, нарушения недопустимы» — атрибут
   аккаунта «шифровать по умолчанию», а не детект через Config постфактум.
2. «Нужно зашифровать существующую базу RDS» — снапшот, копия с шифрованием,
   восстановление.
3. «Ключи должны храниться в устройстве под нашим контролем FIPS 140-2 level 3» —
   CloudHSM или KMS custom key store.
4. «Аудит всех операций с ключом» — customer managed key плюс CloudTrail.
5. «Стоимость KMS выросла из-за миллионов мелких объектов в S3» — S3 Bucket Keys.
6. «Пароли БД должны меняться каждые 30 дней автоматически» — Secrets Manager
   с ротацией.
7. «Данные реплицируются в другой регион и должны оставаться зашифрованными» —
   multi-Region key или ключ целевого региона при копировании.
8. «Приложение обращается к KMS из приватной подсети без интернета» — interface
   endpoint для KMS.

## Политика ключа и доступ

Политика ключа — resource-based политика, без которой identity-политика на KMS не
работает: если политика ключа не делегирует права аккаунту, никакие права пользователя
не помогут. Это отличает KMS от большинства сервисов и регулярно встречается в вопросах
о кросс-аккаунтном доступе к зашифрованным данным.

Стандартная конструкция для доступа из другого аккаунта: в политике ключа перечислен
аккаунт-потребитель с действиями `kms:Decrypt` и `kms:DescribeKey`, а на стороне
потребителя роль получает те же действия в identity-политике. Дополнительно ограничивают
условиями `kms:ViaService` (использовать ключ только через конкретный сервис) и
`kms:EncryptionContext` (только для конкретного ресурса).

Grants — временная делегация прав на ключ сервисам, которые работают от вашего имени;
их выдаёт и отзывает сервис, они удобнее правки политики для краткоживущих операций.

## CloudHSM и требования регуляторов

CloudHSM — выделенный аппаратный модуль под вашим единоличным контролем, FIPS 140-2
level 3, доступ по PKCS#11 и JCE. AWS не имеет доступа к ключам и не может восстановить
их при потере учётных данных. Выбирают, когда регулятор требует single-tenant HSM,
собственную генерацию и хранение ключей или поддержку специфических криптоопераций.
KMS custom key store соединяет удобство KMS с хранением материала в CloudHSM — компромисс
для тех, кто хочет обычные интеграции сервисов при своих ключах.

## Как читать формулировку

| В тексте вопроса | Ответ |
|---|---|
| «control the key policy, rotate, audit usage» | customer managed key |
| «single-tenant HSM, FIPS 140-2 level 3» | CloudHSM |
| «automatically rotate database credentials» | Secrets Manager |
| «store configuration values cheaply» | Parameter Store |
| «KMS request costs spiked on S3» | S3 Bucket Keys |
| «encrypted data replicated to another Region» | multi-Region key |
| «revoke access to encrypted data immediately» | отключить ключ |
| «certificate for CloudFront» | ACM в us-east-1 |

## Числа, которые надо помнить

- KMS шифрует напрямую данные не больше 4 КБ, поэтому всё остальное идёт через
  конвертное шифрование: GenerateDataKey отдаёт ключ данных в открытом и зашифрованном виде;
- автоматическая ротация ключа, управляемого клиентом, происходит раз в год, старый
  материал остаётся для расшифровки прежних данных;
- удаление ключа возможно только после периода ожидания от 7 до 30 дней;
- ключи AWS managed ротируются самим сервисом и их политику нельзя менять;
- multi-Region ключи — единственный способ расшифровать данные в другом регионе тем же
  ключом; обычный ключ строго региональный;
- S3 Bucket Key снижает число обращений к KMS примерно на 99% и заметно уменьшает счёт;
- доступ к ключу определяется политикой ключа: без разрешения в ней политика IAM
  сама по себе доступа не даёт;
- CloudHSM даёт выделенный модуль с уровнем FIPS 140-2 level 3, если требуется полный
  контроль над оборудованием.

## Мини-практикум

**1.** Нужно шифровать файлы в S3 и знать, кто и когда обращался к ключу.
→ SSE-KMS с ключом клиента: обращения видны в CloudTrail. У SSE-S3 такого журнала нет.

**2.** Данные копируются в другой регион и должны читаться там без перешифрования.
→ Multi-Region key: реплика ключа в целевом регионе расшифрует те же данные.

**3.** Затраты на KMS выросли из-за миллионов мелких объектов в бакете.
→ Включить S3 Bucket Key.

**4.** Требуется хранить пароль базы и менять его автоматически раз в месяц.
→ Secrets Manager со встроенной ротацией; Parameter Store дешевле, но ротацию
придётся писать самому.
