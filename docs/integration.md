# Интеграция приложений

Развязка компонентов — сквозная тема экзамена. Слова «decouple», «loosely coupled»,
«buffer», «spikes», «producer must not wait» почти всегда означают очередь или шину,
а не увеличение числа инстансов.

## SQS

Очередь с хранением сообщений до 14 суток (по умолчанию 4 дня), размер сообщения до
256 КБ (больше — через extended client в S3). Потребитель забирает сообщение, оно
становится невидимым на visibility timeout, после успешной обработки удаляется.

| | Standard | FIFO |
|---|---|---|
| Порядок | не гарантирован | строгий в пределах message group |
| Доставка | как минимум один раз | ровно один раз |
| Пропускная способность | практически неограниченная | до 3000 сообщений в секунду с батчингом |
| Дедупликация | нет | по content hash или явному id |

Механики, которые проверяют:

- visibility timeout должен превышать время обработки, иначе сообщение вернётся в
  очередь и будет обработано дважды — типовая причина дублей;
- long polling (`WaitTimeSeconds` до 20) снижает число пустых ответов и стоимость;
- dead-letter queue после N неудачных попыток изолирует «ядовитые» сообщения;
- delay queue и per-message timer откладывают доставку;
- шифрование SSE-KMS и политика очереди для кросс-аккаунтного доступа;
- масштабирование потребителей по метрике `ApproximateNumberOfMessagesVisible`.

## SNS

Публикация и подписка: одно сообщение — много получателей. Подписчики: SQS, Lambda,
HTTP(S), email, SMS, mobile push, Kinesis Data Firehose. Filter policy позволяет
подписчику получать только подходящие сообщения. FIFO-топики работают в паре с FIFO-очередями.

Fan-out (SNS → несколько SQS) — стандартный шаблон, когда одно событие должно попасть
в несколько независимых обработчиков с буферизацией и повторами у каждого.

## EventBridge

Шина событий с маршрутизацией по содержимому: правила сопоставляют JSON-паттерн и
отправляют событие в цели (Lambda, SQS, SNS, Step Functions, API destination и другие).
Отличия от SNS, которые решают выбор:

- события AWS-сервисов приходят на шину по умолчанию — можно реагировать на изменение
  состояния EC2, завершение задачи Batch, изменение в Config;
- партнёрские шины принимают события SaaS (Zendesk, Datadog, Shopify);
- schema registry, архив событий и повторное воспроизведение (replay);
- EventBridge Scheduler запускает цели по расписанию или разово — это про время,
  а не про сопоставление событий;
- API destination вызывает внешний HTTP API с сохранёнными учётными данными.

Правило выбора: нужно разослать своё сообщение многим подписчикам с минимальной
задержкой — SNS; нужно маршрутизировать события (в том числе системные) по содержимому
и хранить историю — EventBridge.

## Step Functions

Государственная машина для процессов: шаги, ветвления, параллель, Map для обработки
коллекций, встроенные ретраи и обработка ошибок, интеграция с сотнями API AWS без кода.
Standard — длительные процессы, exactly-once, оплата за переходы; Express — короткие
и частые, оплата за длительность. Ответ на «оркестрация нескольких Lambda с повторами
и откатами» и на «нужна видимость, на каком шаге упало».

## Amazon MQ

Управляемые ActiveMQ и RabbitMQ с протоколами JMS, AMQP, MQTT, STOMP. Единственная
причина выбирать его вместо SQS/SNS — миграция существующего приложения, которое
использует стандартные протоколы обмена и которое нельзя переписывать.

## Kinesis против очередей

Kinesis Data Streams — упорядоченный поток с воспроизведением и несколькими независимыми
потребителями, данные хранятся до 365 дней. SQS — сообщение исчезает после обработки
одним потребителем. Если в вопросе есть «real-time analytics», «multiple consumers read
the same data», «replay», это Kinesis; если «work queue», «task per message», «buffer
between tiers» — SQS.

## Шаблоны, которые повторяются в вопросах

| Требование | Решение |
|---|---|
| Всплески запросов ломают обработчик | SQS перед обработчиком, автоскейлинг по глубине очереди |
| Один заказ обрабатывают три системы | SNS fan-out в три SQS |
| Порядок операций по клиенту важен | SQS FIFO с message group per client |
| Долгая многошаговая обработка | Step Functions |
| Реакция на события инфраструктуры | EventBridge rule |
| Приложение на JMS переносят в облако | Amazon MQ |
| Аналитика на потоке кликов | Kinesis Data Streams или Firehose |

## Что спрашивают на экзамене

1. «Сообщения теряются при падении обработчика» — очередь вместо прямого вызова.
2. «Часть сообщений обрабатывается дважды» — visibility timeout, идемпотентность,
   при жёстком требовании FIFO.
3. «Одно и то же сообщение нужно четырём подписчикам» — SNS с подписками SQS.
4. «Нужно откладывать обработку на 15 минут» — delay queue или EventBridge Scheduler.
5. «Проблемные сообщения блокируют очередь» — DLQ.
6. «Сообщение весит 10 МБ» — S3 плюс ссылка в сообщении (extended client).
7. «Нужно вызвать внешний SaaS API по событию» — EventBridge API destination.
8. «Нужна видимость шагов и ретраи между сервисами» — Step Functions.

## Числа, которые надо помнить

- SQS: сообщение до 256 КБ, хранение от 60 секунд до 14 суток (по умолчанию 4 дня),
  visibility timeout по умолчанию 30 секунд и до 12 часов, long polling до 20 секунд;
- FIFO: до 3000 сообщений в секунду с батчингом, дедупликация в окне 5 минут;
- SNS: до 12,5 млн подписок на топик, сообщение до 256 КБ;
- EventBridge: событие до 256 КБ, архив и replay, до 5 целей на правило;
- Step Functions Standard: до 1 года на выполнение, Express: до 5 минут;
- Kinesis Data Streams: 1 МБ/с на запись и 2 МБ/с на чтение на шард, хранение до 365 дней.

## Как читать формулировку

| В тексте вопроса | Ответ |
|---|---|
| «decouple», «buffer spikes» | SQS |
| «fan out to multiple subscribers» | SNS с подписками SQS |
| «react to AWS service events» | EventBridge rule |
| «schedule a one-time or recurring task» | EventBridge Scheduler |
| «exactly once, strict order» | SQS FIFO |
| «multiple consumers read the same stream, replay» | Kinesis Data Streams |
| «existing app uses JMS/AMQP» | Amazon MQ |
| «visibility into a multi-step workflow» | Step Functions |

## Диагностика типовых сбоев

| Симптом | Причина | Что делать |
|---|---|---|
| Сообщения обрабатываются дважды | обработка дольше visibility timeout | увеличить timeout, сделать обработчик идемпотентным |
| Очередь растёт | потребителей не хватает | автоскейлинг по глубине очереди, батчинг |
| Одно сообщение блокирует обработку | «ядовитое» сообщение | DLQ с maxReceiveCount |
| Подписчик получает лишние сообщения | нет фильтра | filter policy на подписке SNS |
| События теряются | асинхронный вызов без DLQ | Lambda Destinations или DLQ |
| Порядок нарушен | standard-очередь | FIFO с message group id |

## Мини-практикум

**1.** Веб-приложение вызывает обработчик изображений синхронно, при всплесках
пользователи получают таймауты.
→ Положить задание в SQS и обрабатывать асинхронно, масштабируя потребителей по глубине
очереди.

**2.** Событие «заказ оплачен» должно попасть в биллинг, в склад и в аналитику.
→ SNS-топик с тремя подписками SQS: у каждого потребителя своя очередь, ретраи и DLQ.

**3.** Часть сообщений обрабатывается по два раза.
→ Проверить visibility timeout относительно времени обработки и сделать обработчик
идемпотентным; при жёстком требовании — FIFO-очередь.

**4.** Нужно запускать выгрузку каждый день в 3 часа ночи и реагировать на завершение
задачи AWS Batch.
→ Расписание — EventBridge Scheduler, реакция на событие — правило EventBridge с
паттерном события Batch.
