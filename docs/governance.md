# Управление и наблюдаемость

Блок про то, как держать ландшафт под контролем: структура аккаунтов, журналирование,
соответствие требованиям, автоматизация операций и резервное копирование.

## Organizations и Control Tower

Organizations объединяет аккаунты в дерево OU с консолидированным счётом, SCP и общими
сервисами (CloudTrail organization trail, Config aggregator, RAM). Консолидированный
биллинг даёт объёмные скидки и общие Reserved Instances и Savings Plans на всю
организацию — типовой ответ на «снизить общую стоимость нескольких аккаунтов».

Control Tower разворачивает landing zone: OU по назначению, log archive и audit
аккаунты, guardrails (превентивные на SCP, детективные на Config), Account Factory
для выдачи новых аккаунтов по стандарту. Формулировка «new accounts must automatically
comply» — Control Tower, а не ручные политики.

## CloudTrail

Журнал вызовов API: кто, когда, откуда, с какими параметрами. Management events
пишутся 90 дней в Event history бесплатно; для долгого хранения создают trail в S3,
желательно организационный, в отдельный аккаунт, с включённой валидацией целостности
файлов и шифрованием KMS. Data events (операции с объектами S3, вызовы Lambda) не
пишутся по умолчанию и включаются отдельно — это частая деталь вопроса «мы не видим,
кто удалил объект».

CloudTrail Lake хранит и позволяет запрашивать события SQL-подобным языком; интеграция
с Athena решает ту же задачу поверх S3.

## Config

Записывает конфигурацию ресурсов во времени и оценивает её правилами: «тома должны быть
зашифрованы», «бакеты не должны быть публичными», «инстансы должны иметь тег Owner».
Умеет автоматическую ремедиацию через SSM Automation. Conformance packs собирают наборы
правил под стандарты, aggregator собирает картину по всем аккаунтам и регионам.

Отличие от CloudTrail: CloudTrail отвечает на вопрос «кто это сделал», Config — «в каком
состоянии ресурс сейчас и каким он был раньше». Отличие от превентивного контроля:
Config обнаруживает нарушение постфактум, SCP и настройки по умолчанию не дают его
совершить.

## CloudWatch

- метрики (стандартные и пользовательские), алармы, композитные алармы;
- Logs: группы, потоки, фильтры метрик по шаблону в тексте, Logs Insights для запросов,
  подписки для потоковой доставки в Firehose или Lambda;
- агент CloudWatch собирает память, диск и логи с EC2 и локальных серверов;
- дашборды, Container Insights, Lambda Insights, Application Signals;
- EventBridge (исторически CloudWatch Events) реагирует на события и расписание.

Аларм с действием: уведомление в SNS, автоскейлинг, восстановление инстанса, вызов
Lambda через EventBridge — стандартный ответ на «реагировать автоматически».

## Systems Manager

Набор инструментов эксплуатации: Session Manager (доступ без SSH и bastion), Patch
Manager (окна обслуживания и отчёты о патчах), Run Command, State Manager, Automation
(рантбуки), Inventory, Parameter Store, Fleet Manager. Работает и на EC2, и на локальных
серверах через агент.

Три ответа, которые встречаются постоянно: безопасный доступ к инстансам — Session
Manager; централизованное обновление ОС — Patch Manager; хранение конфигурации —
Parameter Store.

## AWS Backup

Централизованные политики резервного копирования для EBS, EC2, RDS, Aurora, DynamoDB,
EFS, FSx, Storage Gateway, S3 и других сервисов. Планы задают расписание, срок хранения,
переход в холодное хранилище, копирование в другой регион и аккаунт. Vault Lock делает
копии неизменяемыми (WORM) — ответ на регуляторное требование «бэкапы нельзя удалить
раньше срока». Backup Audit Manager проверяет, что все ресурсы покрыты политикой.

## Инфраструктура как код

CloudFormation описывает ресурсы шаблоном, поддерживает change sets, drift detection,
nested stacks и StackSets для развёртывания в множестве аккаунтов и регионов. CDK
генерирует шаблоны из кода на привычном языке. Service Catalog публикует одобренные
продукты, которые команды разворачивают без прав на отдельные сервисы — ответ на
«разрешить командам создавать только согласованные конфигурации».

## Теги и учёт

Теги — основа для распределения затрат, ABAC-доступа, автоматизации и поиска. Tag
Editor и Tag Policies в Organizations поддерживают единообразие; активированные
cost allocation tags появляются в отчётах Cost Explorer и в Cost and Usage Report.

## Что спрашивают на экзамене

1. «Кто удалил объект в бакете» — CloudTrail data events для S3.
2. «Убедиться, что все тома зашифрованы, и починить нарушения» — Config с ремедиацией.
3. «Новые аккаунты должны создаваться по стандарту» — Control Tower Account Factory.
4. «Патчить сотни инстансов по расписанию» — Patch Manager.
5. «Единые бэкапы разных сервисов с хранением 7 лет» — AWS Backup с Vault Lock.
6. «Развернуть одинаковую инфраструктуру в 20 аккаунтах» — CloudFormation StackSets.
7. «Логи приложения нужно анализировать и алертить по шаблону» — CloudWatch Logs
   с фильтром метрик и алармом.
8. «Запретить регионы вне ЕС всем аккаунтам» — SCP.

## Как читать формулировку

| В тексте вопроса | Ответ |
|---|---|
| «who deleted the object» | CloudTrail data events |
| «resource must always be compliant, fix automatically» | Config с ремедиацией |
| «prevent the action entirely» | SCP или настройка по умолчанию, не Config |
| «new accounts follow the standard» | Control Tower Account Factory |
| «patch hundreds of instances» | Patch Manager |
| «backups immutable for seven years» | AWS Backup с Vault Lock |
| «same stack in 20 accounts and Regions» | CloudFormation StackSets |
| «teams deploy only approved configurations» | Service Catalog |

## Централизованное журналирование

Стандартная схема: организационный trail CloudTrail пишет в бакет security-аккаунта
с включённой валидацией и Object Lock; логи VPC Flow Logs и приложений собираются в
CloudWatch Logs с подпиской в Firehose и выгрузкой в тот же бакет; доступ к бакету
имеет только команда безопасности, а прикладные аккаунты не могут удалять объекты.
Такое разделение — типичный правильный вариант в вопросах про защиту доказательств
от администратора-нарушителя.

## Мини-практикум

**1.** Требуется доказать регулятору, кто и когда обращался к объектам бакета.
→ CloudTrail data events для S3 в отдельный бакет security-аккаунта с валидацией
целостности.

**2.** В организации регулярно появляются публичные бакеты.
→ Превентивно: Block Public Access на уровне аккаунтов и SCP; детективно: правило
Config с автоматической ремедиацией.

**3.** Нужно раскатать одинаковый набор ролей и логирования в 25 аккаунтов.
→ CloudFormation StackSets через Organizations.

**4.** Бэкапы должны храниться 7 лет и не удаляться даже администратором.
→ AWS Backup с Vault Lock в режиме соответствия и копией в другой регион.

## Числа, которые надо помнить

- SCP не действует на управляющий аккаунт организации, а к одному узлу иерархии можно
  присоединить до 5 политик;
- событие CloudTrail появляется в журнале обычно в течение 15 минут; история событий
  в консоли хранится 90 дней, всё, что дольше, требует записи в S3;
- события данных (обращения к объектам S3, вызовы функций) по умолчанию выключены и
  тарифицируются отдельно;
- базовый мониторинг EC2 публикует метрики раз в 5 минут, подробный — раз в минуту;
- метрики CloudWatch хранятся 15 месяцев с постепенным укрупнением интервала;
- у журналов CloudWatch Logs срок хранения по умолчанию не ограничен, его задают явно;
- Vault Lock хранилища AWS Backup в режиме compliance необратим после периода
  вызревания в трое суток, в режиме governance снимается пользователем с особым правом;
- Config хранит историю конфигураций ресурсов и позволяет описывать правила
  соответствия, в том числе с автоматическим исправлением.
