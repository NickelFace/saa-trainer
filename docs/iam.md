# IAM

Каждый запрос к AWS проходит проверку: кто (principal), что (action), над чем (resource),
при каких условиях (condition). Разрешение возникает, если есть явный allow и нет ни
одного явного deny. Явный deny выигрывает всегда и на любом уровне.

## Сущности

- Root — владелец аккаунта, может всё, отключить нельзя. Практика: MFA на root, ключи
  доступа root удалить, повседневная работа — под другими идентичностями.
- IAM user — долговременные учётные данные. Годится для людей без SSO и для внешних
  систем, которым нельзя выдать роль. В современных ответах почти всегда проигрывает.
- IAM group — контейнер политик для пользователей, не является principal.
- IAM role — набор разрешений с временными ключами через STS. Основной механизм для
  сервисов AWS, приложений на EC2/ECS/Lambda, кросс-аккаунтного доступа и федерации.
- Identity Center (бывший SSO) — управление доступом людей к множеству аккаунтов через
  корпоративный каталог, permission sets вместо копирования политик.

## Типы политик

| Тип | Прикрепляется к | Назначение |
|---|---|---|
| Identity-based | пользователь, группа, роль | что этой идентичности разрешено |
| Resource-based | бакет, очередь, топик, ключ, функция | кому разрешено обращаться к ресурсу |
| Permissions boundary | пользователь или роль | верхняя граница разрешений идентичности |
| SCP (Organizations) | OU или аккаунт | верхняя граница для всего аккаунта |
| Session policy | сессия STS | сужение прав на время сессии |
| ACL | S3, устаревшее | не использовать в новых решениях |

Как считается итог: эффективные права = (identity-based ∪ resource-based) ∩ boundary ∩
SCP, минус любые явные deny. SCP сами по себе ничего не разрешают — они только
ограничивают. Поэтому «дать доступ через SCP» — всегда неверный вариант.

## Кросс-аккаунтный доступ

Каноническая схема: в аккаунте с ресурсом создаётся роль, в её trust policy указан
principal — аккаунт или роль потребителя; потребитель вызывает `sts:AssumeRole` и
получает временные ключи. Дублировать пользователей в каждом аккаунте не нужно.

Тонкости, которые проверяют:

- trust policy указывает того, кто будет принимать роль, а не тех, кто уже в этом же
  аккаунте: роль в аккаунте A с доверием к самому аккаунту A ничего не решает;
- `sts:ExternalId` защищает от confused deputy при доступе третьей стороны;
- для S3 и других ресурсов с resource-based политикой доступ можно дать напрямую
  политикой ресурса, без принятия роли;
- права принятой роли ограничены пересечением её политики и session policy.

## Федерация

- Корпоративный каталог (AD, Okta, Entra) через SAML 2.0 или Identity Center —
  сотрудники входят своими учётными данными, роли выдаются по группам.
- Web-идентичности и мобильные приложения — Cognito identity pools обменивают токен
  провайдера на временные ключи AWS.
- Cognito user pools — это про аутентификацию пользователей приложения; identity pools —
  про выдачу прав в AWS. В вопросах про «вход через Google/Facebook в мобильном
  приложении и доступ к S3» нужны оба.
- IAM Roles Anywhere выдаёт роли рабочим нагрузкам вне AWS по сертификатам.

## Условия в политиках

Часто встречающиеся ключи: `aws:SourceIp`, `aws:SourceVpce`, `aws:PrincipalOrgID`,
`aws:RequestedRegion`, `aws:MultiFactorAuthPresent`, `s3:x-amz-server-side-encryption`,
`ec2:ResourceTag/...`. Это инструмент для требований вида «доступ только из офисной
сети», «только из нашей организации», «только при включённой MFA», «только к ресурсам
с тегом проекта» (ABAC).

ABAC — управление доступом по тегам: одна политика вида «разрешить действия, если тег
ресурса совпадает с тегом принципала» заменяет десятки политик под отдельные проекты
и не требует правок при добавлении новой команды.

## Инструменты контроля

- IAM Access Analyzer находит ресурсы с внешним доступом, проверяет политики на ошибки
  и генерирует политику по фактическим вызовам из CloudTrail;
- Credential report и Access Advisor показывают неиспользуемые ключи и права —
  основа для сокращения привилегий;
- Access Analyzer + permission boundaries — типовой ответ на «дать командам создавать
  роли, но не дать им повысить себе привилегии».

## Что спрашивают на экзамене

1. «Приложение на EC2 обращается к S3» — роль на инстансе, не ключи в файле и не
   пользователь IAM.
2. «Разработчикам нужен доступ к продуктовому аккаунту» — роль в целевом аккаунте
   с доверием к аккаунту разработки.
3. «Запретить всем аккаунтам использовать регионы вне ЕС» — SCP с deny по
   `aws:RequestedRegion`.
4. «Команды сами создают роли, но не могут расширить свои права» — permissions boundary.
5. «Единый вход сотрудников во все аккаунты» — Identity Center с федерацией.
6. «Доступ подрядчику к нашему бакету» — роль с ExternalId или bucket policy с его
   аккаунтом, ни в коем случае не общие ключи.
7. «Секреты приложения с автоматической ротацией» — Secrets Manager, а не IAM.
8. «Сократить права до фактически используемых» — Access Advisor или сгенерированная
   Access Analyzer политика.

## Структура политики

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "OnlyFromOfficeWithMFA",
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::reports/*",
    "Condition": {
      "IpAddress": {"aws:SourceIp": "203.0.113.0/24"},
      "Bool": {"aws:MultiFactorAuthPresent": "true"}
    }
  }]
}
```

Что читают в вопросах: `Resource` с `*` — признак избыточных прав; действие уровня
бакета (`s3:ListBucket`) требует ARN бакета, а не объектов; `NotAction` и `NotResource`
почти всегда ошибка проектирования; отсутствие `Condition` там, где требование говорит
«только из корпоративной сети», делает вариант неверным.

## Организация аккаунтов

Organizations объединяет аккаунты в дерево OU с единым счётом и SCP. Типовая структура:
отдельные OU для production, non-production, security и sandbox; логи CloudTrail и
Config собираются в выделенный security-аккаунт, куда у прикладных команд нет доступа
на удаление.

Control Tower разворачивает эту структуру автоматически: landing zone, guardrails
(превентивные через SCP и детективные через Config), Account Factory для выдачи новых
аккаунтов по шаблону. Требование «новые аккаунты должны сразу соответствовать стандарту»
всегда решается Control Tower, а не ручными политиками.

## Временные учётные данные

STS выдаёт ключи с ограниченным сроком: `AssumeRole` для ролей внутри и между аккаунтами,
`AssumeRoleWithSAML` для корпоративной федерации, `AssumeRoleWithWebIdentity` для
Cognito и OIDC-провайдеров, включая IRSA в EKS. Максимальная длительность сессии
задаётся ролью (до 12 часов), цепочка ролей ограничена одним часом. Отзыв доступа
до истечения срока делается политикой с условием `aws:TokenIssueTime` или отключением
роли — это спрашивают в вопросах про компрометацию.
