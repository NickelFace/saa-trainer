# Aurora

Aurora совместима с MySQL и PostgreSQL по протоколу, но хранилище у неё своё:
распределённый том, растущий до 128 ТБ, с шестью копиями каждого блока в трёх зонах
доступности. Кластер переживает потерю двух копий без потери данных и трёх копий без
потери доступности на чтение. Отсюда все её свойства: быстрый failover, дешёвые реплики,
клонирование и восстановление на любой момент времени.

## Устройство кластера

- writer — единственный инстанс, принимающий запись;
- до 15 reader-инстансов, читающих тот же том, отставание обычно десятки миллисекунд;
- хранилище общее и самовосстанавливающееся, реплики не копируют данные;
- при отказе writer один из readers становится writer обычно за считанные секунды,
  порядок задаётся приоритетом (tier) инстансов.

Endpoints — то, что чаще всего проверяют:

| Endpoint | Куда ведёт | Когда использовать |
|---|---|---|
| Cluster (writer) | текущий writer | запись, следует за failover |
| Reader | балансировка между readers | чтение приложения |
| Custom | заданное подмножество инстансов | отдельный пул для отчётов или BI |
| Instance | конкретный инстанс | диагностика, точечные задачи |

Приложение должно использовать reader endpoint для чтения; если в варианте ответа
чтение направляют на cluster endpoint, вариант неверный.

## Типы хранилища и цена

У Aurora только два типа конфигурации хранилища: Standard и I/O-Optimized. Термины
gp2, gp3, Provisioned IOPS относятся к RDS и EBS, но не к кластеру Aurora — это готовая
ловушка. Standard тарифицирует операции ввода-вывода отдельно, I/O-Optimized включает
их в цену инстансов и выгоден при доле I/O выше примерно 25 процентов счёта.

Общая структура стоимости: инстансы (или ACU в Serverless), хранилище за ГБ, операции
I/O в Standard, бэкапы сверх размера кластера, трафик между зонами и регионами.

## Serverless v2

Serverless v2 масштабирует ёмкость инстанса непрерывно в единицах ACU (0.5 ACU и выше,
с 2024 года возможен масштаб до нуля для отдельных конфигураций), не разрывая
соединения. Подходит для непредсказуемой и «пилообразной» нагрузки, для dev-окружений
и для мультитенантных приложений. Важная деталь для вопросов про экономию: обычный
provisioned-кластер можно остановить максимум на 7 суток, дальше он запускается сам,
а Serverless v2 сам масштабируется вниз в простое.

## Global Database

Aurora Global Database реплицирует данные в до 10 вторичных регионов с типичной
задержкой менее секунды. Вторичный регион даёт локальное чтение и позволяет выполнить
promote за примерно минуту: RPO измеряется секундами, RTO — минутами. Это стандартный
ответ на «глобальное приложение с чтением по регионам и быстрым восстановлением после
отказа региона». Кросс-региональная read replica RDS работает медленнее и переключается
дольше.

## Клоны, бэкапы, восстановление

- Backtrack (только MySQL-совместимая версия) отматывает кластер на несколько часов
  назад за минуты, без восстановления снапшота — ответ на «откатить ошибочный
  DELETE максимально быстро»;
- fast database cloning создаёт копию через copy-on-write за минуты и почти без
  дополнительного места — ответ на «нужна копия prod для тестов»;
- непрерывный бэкап в S3 даёт PITR в пределах срока хранения;
- снапшоты можно копировать между регионами и аккаунтами.

## Дополнительные возможности

- Aurora Auto Scaling добавляет readers по метрике загрузки;
- параллельный запрос (Parallel Query) в MySQL-совместимой версии ускоряет аналитические
  запросы, перенося фильтрацию в слой хранения;
- Aurora Machine Learning вызывает SageMaker и Comprehend прямо из SQL;
- Zero-ETL интеграция с Redshift переносит данные в аналитику без конвейера;
- Babelfish принимает соединения от приложений SQL Server к Aurora PostgreSQL — ответ
  на «мигрировать с SQL Server, не переписывая клиентский код».

## Aurora против RDS

| Требование | Выбор |
|---|---|
| Максимальная пропускная способность и до 15 реплик | Aurora |
| Failover за секунды | Aurora |
| Движки Oracle, SQL Server, Db2 | RDS |
| Минимальная стоимость небольшой стабильной базы | RDS |
| Копии окружения для тестов «на лету» | Aurora (fast clone) |
| Глобальное чтение с RPO в секунды | Aurora Global Database |
| Нагрузка два часа в неделю | Aurora Serverless v2 или остановка RDS |

## Что спрашивают на экзамене

1. «Отчётные запросы не должны мешать записи» — reader endpoint или custom endpoint
   на отдельные инстансы.
2. «Нужна копия боевой базы для тестирования сегодня к вечеру» — fast clone.
3. «Разработчик удалил таблицу час назад» — Backtrack (MySQL) или PITR.
4. «Приложение в трёх регионах, локальное чтение, отказ региона переживаем за минуты» —
   Global Database.
5. «Нагрузка непредсказуема, платить за простой не хотим» — Serverless v2.
6. «Счёт вырос из-за операций ввода-вывода» — I/O-Optimized.
7. «Нужно смасштабировать запись» — вертикальный рост writer или шардирование;
   реплики запись не масштабируют.
8. «Совместимость с приложением на SQL Server без переписывания» — Babelfish.

## Числа, которые надо помнить

- 6 копий данных в 3 AZ, потеря 2 копий не мешает записи, потеря 3 — чтению;
- до 15 reader-инстансов, отставание десятки миллисекунд;
- том растёт до 128 ТБ автоматически, шагами по 10 ГБ;
- failover обычно менее 30 секунд, у Multi-AZ instance RDS — 60–120 секунд;
- Global Database: до 10 вторичных регионов, задержка репликации около секунды,
  promote примерно за минуту;
- Backtrack до 72 часов назад (только MySQL-совместимая версия);
- Serverless v2 масштабируется шагами 0.5 ACU без разрыва соединений.

## Как читать формулировку

| В тексте вопроса | Ответ |
|---|---|
| «read-heavy, reports slow down writes» | reader endpoint или дополнительные readers |
| «need a copy of production for testing quickly» | fast clone |
| «accidentally dropped a table an hour ago» | Backtrack или PITR |
| «users in three continents, local reads» | Global Database |
| «unpredictable, spiky workload» | Serverless v2 |
| «I/O charges dominate the bill» | I/O-Optimized |
| «must support Oracle» | это не Aurora, а RDS |
| «application uses SQL Server drivers» | Babelfish на Aurora PostgreSQL |

## Что Aurora не решает

Запись масштабируется только вертикально: reader-инстансы не принимают запись,
и вопрос «как масштабировать запись» решается более крупным writer, разделением
данных по кластерам или переходом на DynamoDB, если модель данных это допускает.
Aurora не превращает реляционную нагрузку в бессерверную бесплатно: Serverless v2
тарифицируется за ACU-часы и при постоянной нагрузке дороже provisioned-кластера.

## Мини-практикум

**1.** Кластер Aurora MySQL обслуживает интернет-магазин. Аналитики жалуются, что их
отчёты идут минутами и мешают оформлению заказов. Что сделать?
→ Custom endpoint на выделенные reader-инстансы: отчёты уходят на свои узлы, writer
остаётся под заказами.

**2.** Разработчику нужна копия боевой базы объёмом 4 ТБ до конца дня, бюджет ограничен.
→ Fast database clone: копия создаётся за минуты по copy-on-write и почти не занимает
дополнительного места.

**3.** Кластер работает два часа в неделю, остальное время простаивает.
→ Aurora Serverless v2: масштабируется вниз в простое; provisioned-кластер можно
остановить максимум на 7 суток, дальше он запустится сам.

**4.** Приложение работает в трёх регионах, требуется локальное чтение и восстановление
после отказа региона за минуты.
→ Aurora Global Database: репликация около секунды, promote вторичного региона примерно
за минуту.
