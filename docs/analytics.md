# Аналитика

Блок с большим количеством похожих сервисов. Разбирать вопрос удобно по цепочке:
как данные попадают в облако (ingest) → где лежат (storage) → чем обрабатываются
(process) → чем показываются (visualize).

## Kinesis

| Сервис | Назначение | Особенности |
|---|---|---|
| Data Streams | приём и хранение потока | шарды или on-demand, хранение до 365 дней, много потребителей, порядок в шарде |
| Data Firehose | доставка потока в приёмник | без администрирования, буферизация, преобразование Lambda, приёмники S3, Redshift, OpenSearch, Splunk |
| Managed Service for Apache Flink | потоковая аналитика | SQL и Flink-приложения поверх потока |
| Video Streams | видеопотоки | приём с камер, интеграция с ML |

Разница, которую проверяют: Data Streams — если нужен произвольный доступ к данным,
несколько независимых потребителей, повтор чтения и минимальная задержка; Firehose —
если задача «просто сложить поток в S3/Redshift/OpenSearch без кода и серверов».
Firehose имеет буфер (обычно от 60 секунд), поэтому «доставка в near real-time» ему
подходит, а «обработка за миллисекунды» — нет.

SQS в этом ряду решает другую задачу: очередь заданий, а не поток для аналитики.

## Хранение и каталог

S3 — фактический слой данных для аналитики (data lake). Формат имеет значение:
колоночные Parquet и ORC сокращают объём сканирования, а значит стоимость Athena и
время запроса; партиционирование по дате и ключу сокращает его ещё сильнее.

Glue Data Catalog — метаданные таблиц для Athena, EMR, Redshift Spectrum; Glue Crawler
определяет схему автоматически; Glue ETL (Spark) и Glue Studio выполняют преобразования
без серверов. Lake Formation добавляет централизованные права на таблицы, колонки и
строки поверх каталога.

## Обработка и запросы

| Сервис | Модель | Когда выбирают |
|---|---|---|
| Athena | SQL по данным в S3, оплата за просканированные байты | разовые и нерегулярные запросы, логи, минимум администрирования |
| Redshift | MPP-хранилище с загруженными данными | постоянная тяжёлая аналитика, сложные join, BI на терабайтах |
| Redshift Spectrum | запросы Redshift к данным в S3 | горячая часть в кластере, холодная в озере |
| EMR | Hadoop, Spark, Hive, Presto на кластере | существующие job на Spark/Hadoop, тонкая настройка, ML-пайплайны |
| OpenSearch | поисковый и лог-анализ | полнотекстовый поиск, дашборды по логам, near real-time |
| QuickSight | BI-дашборды | визуализация для бизнеса, SPICE-кэш, ML insights |

Правило выбора между Athena и Redshift: если в вопросе «ad-hoc», «occasionally»,
«no infrastructure to manage», «data already in S3» — Athena; если «complex joins»,
«consistent high query volume», «data warehouse», «BI team runs reports all day» —
Redshift.

## Redshift подробнее

Узлы RA3 отделяют вычисления от хранилища (Managed Storage), Serverless убирает
кластер вовсе. Возможности из вопросов: Concurrency Scaling добавляет мощность на пики
чтения, materialized views ускоряют повторяющиеся запросы, data sharing даёт доступ
к данным другого кластера без копирования, cross-Region snapshot — часть DR-плана,
Zero-ETL из Aurora избавляет от конвейера.

## ElastiCache в аналитике и не только

Redis и Memcached в управляемом виде. Redis: репликация, Multi-AZ с автофейловером,
persistence, структуры данных, pub/sub, sorted set для лидербордов, кластеризация.
Memcached: простой кэш, многопоточность, горизонтальное расширение, без репликации и
persistence.

Типовые ответы: кэш горячих запросов перед RDS, хранение сессий, лидерборды, rate
limiting. Если требуется durability и failover — Redis; если нужен простейший кэш с
масштабированием по нодам — Memcached.

## Типовые конвейеры

- Логи приложений → Firehose → S3 → Athena/QuickSight (дёшево, near real-time).
- Клики → Data Streams → Flink → DynamoDB/OpenSearch (аналитика в реальном времени).
- Файлы партнёров → S3 → Glue Crawler → Glue ETL → Redshift → QuickSight.
- Данные IoT → IoT Core → Firehose → S3 → Athena.
- Поиск и мониторинг логов → OpenSearch с дашбордами.

## Что спрашивают на экзамене

1. «Запросить логи в S3 SQL-запросом без инфраструктуры» — Athena.
2. «Собирать поток и класть в S3 без кода» — Firehose.
3. «Несколько приложений читают один поток независимо» — Kinesis Data Streams.
4. «Хранилище для BI с постоянной нагрузкой» — Redshift.
5. «Существующие Spark-задачи перенести в облако» — EMR.
6. «Полнотекстовый поиск и дашборды по логам» — OpenSearch.
7. «Снизить стоимость запросов Athena» — Parquet, партиционирование, сжатие.
8. «Централизованно выдавать права на таблицы озера» — Lake Formation.

## Числа, которые надо помнить

- Kinesis Data Streams: шард даёт 1 МБ/с или 1000 записей в секунду на запись и
  2 МБ/с на чтение, запись до 1 МБ, хранение от 24 часов до 365 дней;
- Firehose: буфер по размеру (1–128 МБ) или времени (60–900 секунд), поэтому доставка
  near real-time, а не мгновенная;
- Athena тарифицируется за просканированные байты, Parquet и партиционирование
  сокращают их в разы;
- Redshift RA3 отделяет вычисления от хранилища, Concurrency Scaling добавляет
  мощность на пики;
- OpenSearch хранит горячие, тёплые (UltraWarm) и холодные данные с разной ценой;
- QuickSight SPICE — кэш в памяти для быстрых дашбордов.

## Как читать формулировку

| В тексте вопроса | Ответ |
|---|---|
| «ad-hoc SQL over data already in S3» | Athena |
| «data warehouse, complex joins, BI all day» | Redshift |
| «stream to S3 with no code» | Kinesis Data Firehose |
| «multiple consumers, replay the stream» | Kinesis Data Streams |
| «existing Spark and Hadoop jobs» | EMR |
| «full-text search and log dashboards» | OpenSearch |
| «reduce Athena cost» | Parquet, партиционирование, сжатие |
| «fine-grained permissions on lake tables» | Lake Formation |

## Как отличить похожие пары

Firehose против Data Streams: если данные нужно только доставить в хранилище и не
обрабатывать в полёте — Firehose; если несколько приложений читают один поток и важен
контроль за позицией чтения — Data Streams.

Athena против Redshift Spectrum: Athena самостоятельна и не требует кластера; Spectrum
имеет смысл там, где кластер Redshift уже есть и нужно дотянуться до холодных данных
в S3 в одном запросе с горячими.

OpenSearch против Athena: OpenSearch держит индекс и отвечает за миллисекунды на
поисковые запросы, Athena сканирует файлы и отвечает за секунды и минуты; логи для
интерактивного расследования — OpenSearch, редкие отчёты — Athena.

ElastiCache против DAX: DAX понимает API DynamoDB и не требует правок кода,
ElastiCache универсален, но кэш нужно наполнять и инвалидировать самому.

## Мини-практикум

**1.** Логи ALB накопились в S3, аналитик хочет несколько запросов в неделю.
→ Athena по данным в S3, желательно с партиционированием по дате.

**2.** Поток кликов нужно складывать в S3 и параллельно строить агрегаты в реальном
времени.
→ Kinesis Data Streams: один потребитель — Firehose в S3, второй — Flink для агрегатов.

**3.** Финансовый отдел строит отчёты по терабайтам данных весь рабочий день.
→ Redshift (RA3) с материализованными представлениями и Concurrency Scaling.

**4.** Инженерам нужен поиск по логам приложений с дашбордами и алертами.
→ OpenSearch с доставкой логов через Firehose и UltraWarm для старых индексов.
