# DynamoDB

Ключ-значение и документное хранилище с предсказуемой задержкой в единицы миллисекунд
и без серверов для администрирования. Данные автоматически разложены по партициям в
трёх зонах доступности, ёмкость и хранилище растут без вмешательства.

## Модель данных

- таблица состоит из элементов (item) до 400 КБ;
- primary key: только partition key либо partition key + sort key;
- partition key определяет партицию — от его кардинальности зависит равномерность
  нагрузки; «горячий» ключ упирается в лимит партиции;
- атрибуты не описываются заранее, кроме тех, что входят в ключи и индексы;
- запросы: `GetItem` по ключу, `Query` по partition key с условием на sort key,
  `Scan` по всей таблице (дорого, использовать только осознанно).

## Индексы

| | LSI | GSI |
|---|---|---|
| Когда создаётся | только при создании таблицы | в любой момент |
| Partition key | тот же, что у таблицы | любой |
| Согласованность | возможна строгая | только eventual |
| Ёмкость | общая с таблицей | собственная |
| Лимит | 5 на таблицу, 10 ГБ на partition key | 20 на таблицу |

Практический вывод: почти все ответы на «нужно искать по другому атрибуту» — это GSI.
LSI появляется в ответах, только когда требуется строго согласованное чтение по
альтернативному sort key и индекс можно было завести заранее.

## Режимы ёмкости

- On-demand: платите за запросы, мгновенно принимает всплески, идеален для
  непредсказуемой нагрузки и новых приложений;
- Provisioned: дешевле при стабильной нагрузке, задаются RCU и WCU, дополняется
  auto scaling и Reserved Capacity.

1 RCU = одно строго согласованное чтение элемента до 4 КБ в секунду (или два eventual);
1 WCU = одна запись элемента до 1 КБ в секунду. Transactional-операции стоят вдвое.
При резком росте с тысяч до миллионов пользователей on-demand выигрывает: auto scaling
provisioned-ёмкости реагирует с задержкой в минуты.

## Согласованность и транзакции

По умолчанию чтение eventual consistent — реплика может отставать на доли секунды.
Строго согласованное чтение запрашивается флагом и стоит вдвое дороже, в GSI недоступно.
TransactWriteItems и TransactGetItems дают ACID в пределах региона и до 100 элементов.
Условная запись (`ConditionExpression`) — штатный способ реализовать оптимистичную
блокировку и идемпотентность.

## Streams и событийная обработка

DynamoDB Streams хранит изменения 24 часа и вызывает Lambda для каждой записи: аудит,
агрегация, репликация в OpenSearch, отправка уведомлений. Kinesis Data Streams for
DynamoDB даёт более долгое хранение и другие потребители. Требование «реагировать на
изменение данных» решается стримом, а не опросом таблицы по расписанию.

## Производительность и кэширование

- DAX — кэш в памяти перед таблицей, снижает задержку чтения до микросекунд, работает
  прозрачно для API DynamoDB, живёт в VPC. Ответ на «чтение горячих данных должно быть
  быстрее миллисекунд» без переписывания приложения;
- ElastiCache уместен, когда кэшируются агрегаты и результаты запросов, а не элементы
  таблицы;
- Adaptive capacity сглаживает неравномерность, но не спасает от по-настоящему горячего
  ключа: проектируйте распределяющий partition key (например, добавляя суффикс).

## Хранение, TTL и бэкапы

- TTL удаляет устаревшие элементы бесплатно — типовой ответ на «удалять записи старше
  N дней автоматически»;
- PITR восстанавливает состояние на любую секунду за последние 35 дней;
- по требованию делаются полные бэкапы, интеграция с AWS Backup;
- экспорт в S3 без влияния на производительность таблицы, дальше Athena или Glue;
- Standard-IA класс таблицы дешевле хранит редко читаемые данные.

## Глобальные таблицы

Global tables — мультирегиональная репликация с активной записью во всех регионах,
разрешение конфликтов «последняя запись побеждает», требуют включённых Streams.
Ответ на «пользователи по всему миру пишут и читают локально, регион может отказать».

## Что спрашивают на экзамене

1. «Каталог товаров с непредсказуемой нагрузкой и запросами по ключу» — DynamoDB
   on-demand.
2. «Нужно искать по не ключевому полю» — GSI.
3. «Хранить сессии веб-приложения» — DynamoDB с TTL (или ElastiCache при жёсткой
   задержке).
4. «Реагировать на каждое изменение записи» — Streams плюс Lambda.
5. «Микросекундная задержка чтения без правки кода» — DAX.
6. «Мультирегиональное приложение с записью в каждом регионе» — global tables.
7. «Аналитика по данным DynamoDB» — экспорт в S3 и Athena, а не Scan по таблице.
8. «Сложные join и отчётность» — это не DynamoDB, а реляционная база.

## Числа, которые надо помнить

- элемент до 400 КБ, partition key до 2048 байт, sort key до 1024 байт;
- 1 RCU = 1 строго согласованное чтение 4 КБ в секунду (2 eventual), 1 WCU = запись 1 КБ;
- транзакции стоят вдвое и охватывают до 100 элементов;
- партиция выдерживает около 3000 RCU и 1000 WCU;
- Query возвращает до 1 МБ за вызов, дальше пагинация;
- 20 GSI и 5 LSI на таблицу, LSI ограничен 10 ГБ на значение partition key;
- Streams хранят изменения 24 часа, PITR — 35 дней;
- BatchGetItem до 100 элементов, BatchWriteItem до 25.

## Как читать формулировку

| В тексте вопроса | Ответ |
|---|---|
| «key-value access, single-digit millisecond» | DynamoDB |
| «microsecond reads without code changes» | DAX |
| «query by an attribute that is not the key» | GSI |
| «delete records older than 90 days automatically» | TTL |
| «react to every item change» | Streams плюс Lambda |
| «write locally in multiple Regions» | global tables |
| «unpredictable traffic, no capacity planning» | on-demand |
| «complex joins and ad-hoc SQL» | реляционная база, не DynamoDB |

## Проектирование ключа

Ошибки моделирования дают больше провалов, чем нехватка ёмкости. Признаки плохого
ключа: одно значение partition key обслуживает большую часть трафика (например,
дата как ключ для ленты событий), Scan используется как штатный способ чтения, для
каждого нового запроса требуется новый GSI. Приёмы: суффиксы и хеш в ключе для
разбрасывания нагрузки, составной sort key вида `ORDER#2026-05-14` для диапазонных
запросов, single-table design с полем типа сущности, вынесение агрегатов в отдельные
элементы, обновляемые Streams-обработчиком.

## Мини-практикум

**1.** Игровое приложение выросло с тысяч до миллионов пользователей за неделю, всплески
непредсказуемы, простой недопустим.
→ On-demand capacity: принимает всплески мгновенно, автоскейлинг provisioned-ёмкости
реагирует минутами.

**2.** Нужно находить заказы по email клиента, а ключ таблицы — идентификатор заказа.
→ GSI с partition key email; LSI не подходит, его нельзя добавить после создания
таблицы и он требует того же partition key.

**3.** Каждое изменение записи должно попадать в поисковый индекс.
→ DynamoDB Streams плюс Lambda, пишущая в OpenSearch.

**4.** Аналитикам нужен полный выгруз таблицы для BI без влияния на приложение.
→ Export to S3 и запросы Athena; Scan по таблице съест ёмкость и замедлит приложение.
