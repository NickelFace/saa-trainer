# Балансировщики и Auto Scaling

Связка «ELB перед Auto Scaling group в нескольких AZ» — базовый шаблон отказоустойчивости
на экзамене. Балансировщик даёт единую точку входа и проверки здоровья, ASG отвечает
за количество инстансов и замену отказавших.

## Типы балансировщиков

| | ALB | NLB | GWLB | CLB (устарел) |
|---|---|---|---|---|
| Уровень | 7 (HTTP/HTTPS/gRPC) | 4 (TCP/UDP/TLS) | 3 (GENEVE) | 4 и 7 |
| Маршрутизация | по хосту, пути, заголовку, query, методу | по порту | весь трафик в устройства | базовая |
| Производительность | высокая | миллионы запросов, минимальная задержка | зависит от appliance | низкая |
| Статический IP | нет, только DNS | да, Elastic IP на AZ | нет | нет |
| Целевые типы | instance, IP, Lambda | instance, IP, ALB | appliance | instance |
| TLS termination | да | да (TLS listener) | нет | да |
| Sticky sessions | cookie балансировщика или приложения | по source IP | — | cookie |

Как выбирают на экзамене:

- нужен разбор URL, хостов, аутентификация через Cognito или OIDC, WAF — ALB;
- нужен UDP, статический IP, экстремально низкая задержка, TLS passthrough — NLB;
- нужно пропустить трафик через сторонние firewall-устройства — GWLB;
- «WAF должен защищать» — WAF цепляется к ALB, CloudFront, API Gateway и AppSync,
  но не к NLB.

Полезные детали: ALB поддерживает redirect HTTP в HTTPS и фиксированные ответы без
бэкенда; target group с типом Lambda позволяет ALB вызывать функцию; cross-zone
balancing у ALB включён всегда и бесплатен, у NLB выключен по умолчанию и включается
явно; для доступа к приложению по нескольким доменам используется SNI с несколькими
сертификатами.

## Health checks

Проверки бывают на двух уровнях: балансировщик проверяет цель по протоколу и пути,
ASG использует либо EC2 status checks, либо результат проверки ELB. Если ASG настроен
только на EC2 status checks, зависшее приложение на живом инстансе не будет заменено —
классическая ловушка. Правильный ответ: включить ELB health check в качестве типа
проверки ASG.

## Auto Scaling group

Основные параметры: launch template (версионируемый, рекомендуется вместо launch
configuration), min/desired/max, список подсетей в разных AZ, политика прогрева
(warm-up), health check type и grace period, termination policy.

Политики масштабирования:

| Политика | Что делает | Когда |
|---|---|---|
| Target tracking | держит метрику у цели (например, CPU 50%) | почти всегда, самый простой ответ |
| Step scaling | разные шаги для разных порогов тревоги | нужна разная реакция на разные уровни |
| Simple scaling | один шаг с периодом охлаждения | устаревший вариант |
| Scheduled | масштабирование по расписанию | известные пики: рабочие часы, отчётность |
| Predictive | ML-прогноз по истории, провиженинг заранее | регулярные повторяющиеся паттерны |

Практические тонкости:

- метрика может быть не только CPU: ALBRequestCountPerTarget, глубина очереди SQS
  (через custom metric «сообщений на инстанс»), сетевой трафик;
- предиктивное масштабирование обучается на повторяющихся паттернах и плохо реагирует
  на редкие непредсказуемые всплески;
- lifecycle hooks дают время на прогрев кэша при запуске и на слив соединений и выгрузку
  логов при остановке;
- warm pool заранее держит подготовленные, но остановленные инстансы для быстрого старта;
- instance refresh катит новую версию launch template постепенно;
- ASG может создаваться в нескольких AZ, и это дешёвый способ выполнить требование
  «пережить отказ зоны».

## Отказоустойчивость и стоимость

Требование «выдержать отказ AZ» = минимум две AZ и такое min, чтобы оставшиеся зоны
несли нагрузку. Требование «максимально дёшево» + «нагрузка может прерваться» = mixed
instances policy со Spot. Требование «мгновенно отдавать статику» = вынести статику
в S3 и CloudFront, а не увеличивать число инстансов.

Connection draining (deregistration delay) даёт активным соединениям завершиться при
выводе инстанса — правильный ответ для «пользователи получают ошибки при масштабировании
вниз или при деплое».

## Что спрашивают на экзамене

1. «Пользователи теряют сессию при масштабировании» — вынести состояние в ElastiCache
   или DynamoDB; sticky sessions это обходной путь, а не хранение данных.
2. «Зависшее приложение не заменяется» — health check type = ELB.
3. «Нагрузка предсказуемо растёт по будням в 9 утра» — scheduled scaling.
4. «Нужен фиксированный IP для белого списка партнёра» — NLB с Elastic IP или Global
   Accelerator, ALB не подходит.
5. «Балансировка между EC2 и локальным дата-центром» — target group с типом IP.
6. «Обработчики должны масштабироваться по длине очереди» — метрика SQS
   ApproximateNumberOfMessages на инстанс, target tracking.
7. «Минимум операционной работы для веб-приложения с автоскейлингом» — Elastic Beanstalk
   или ECS Fargate, а не ручная сборка ASG.

## Типовой шаблон трёхуровневого приложения

```
Route 53 -> CloudFront -> ALB (public subnets, 2+ AZ)
             |                 -> ASG с веб-инстансами (private subnets)
             |                        -> внутренний ALB -> ASG приложения
             |                                                -> RDS Multi-AZ / Aurora
статика -> S3 (origin CloudFront с OAC)
```

Что здесь проверяют: балансировщик стоит в публичных подсетях, инстансы — в приватных,
security group инстансов разрешает трафик только от security group балансировщика (не
от диапазона CIDR), база принимает подключения только от security group приложения.
Ссылка группы на группу вместо CIDR — маркер правильного ответа в вопросах о безопасности
такой схемы.

## Диагностика типовых симптомов

| Симптом | Причина | Решение |
|---|---|---|
| 502 и 504 от ALB | цель не отвечает или таймаут приложения | проверить health check, увеличить idle timeout |
| Инстансы циклически заменяются | health check строже, чем время старта приложения | увеличить health check grace period |
| Ошибки при масштабировании вниз | соединения обрываются | deregistration delay, lifecycle hook |
| Нагрузка неравномерна по AZ | выключен cross-zone у NLB | включить cross-zone balancing |
| Долгий отклик после простоя | холодный старт инстансов | warm pool, предиктивное масштабирование |

## Стоимость балансировки

Плата состоит из почасовой ставки и LCU (или NLCU) — единиц, которые считают новые
соединения, активные соединения, пропускную способность и правила. Отсюда практические
выводы: лишние правила маршрутизации на ALB стоят денег, длинные keep-alive соединения
дешевле частых новых, а трафик, отданный CloudFront, вообще не доходит до балансировщика
и не тарифицируется как LCU. Cross-zone трафик у NLB между AZ оплачивается отдельно —
ещё один аргумент против включения его без необходимости.

## Слушатели, правила и сертификаты

Listener принимает соединения на порту и протоколе, правила разбирают запрос по
условиям: host-header, path, http-header, query-string, source-ip, http-request-method.
Действия: forward в target group (с весами для canary-выката), redirect, fixed-response,
authenticate-cognito и authenticate-oidc. Аутентификация на ALB закрывает требование
«пускать только сотрудников» без правок в приложении.

Сертификаты: один по умолчанию плюс дополнительные через SNI, что позволяет обслуживать
десятки доменов одним ALB. Политика безопасности listener задаёт минимальную версию TLS —
типовой ответ на требование «запретить TLS ниже 1.2».
