## Разобранные вопросы с низкой уверенностью (6)

Разобраны 2026-08-25, отдельного статуса «низкая уверенность» в банке больше нет.

- **#113**: ключ C сохранён, помечен спорным. Snowcone (8 или 14 ТБ) не вмещает 50 ТБ,
  DataSync требует полосы, которой у дата-центра нет — остаются C и D. C переписывает
  кастомное приложение как job в Glue (нет администрирования, но есть разработка
  заново), D переносит существующее приложение на EC2 (работает как есть, но инстанс
  надо обслуживать). Формулировка «least operational overhead» допускает оба чтения.
- **#308**: BD -> **BC**. Инстансы в тексте названы active, а проверка Trusted Advisor
  «Amazon RDS Idle DB Instances» ищет базы без подключений и на активных не сработает.
  Стоимость постоянно работающих 90 дней инстансов снижает проверка «Amazon RDS
  Reserved Instance Optimization», а рекомендации по RI консолидируются в аккаунте
  плательщика.
- **#350**: ключ AC подтверждён. Требования действительно два, и варианты закрывают
  каждое по отдельности: A (Multi-AZ) даёт высокую доступность и автоматическое
  восстановление, C (read replica в другой AZ для отчётов) снимает отчётную нагрузку
  с основного инстанса. RDS for SQL Server поддерживает read replicas в редакции
  Enterprise.
- **#422**: ключ D подтверждён. Остальные варианты содержат технические дефекты: NLB
  не умеет вызывать Lambda (это умеет ALB), App Mesh это service mesh, а не механизм
  масштабирования, а «AWS Auto Scaling для увеличения числа vCPU у Lambda» не
  существует. Остаётся SQS плюс ECS с автоскейлингом по длине очереди.
- **#511**: ключ C сохранён, помечен спорным, добавлена пометка о дефекте варианта.
  В дампе вариант C напечатан как «Aurora On-Demand PostgreSQL-Compatible» и в таком
  виде дублирует вариант A; по смыслу задачи (среда используется 4 часа из 8-часового
  дня) там должен стоять Aurora Serverless. При буквальном чтении варианта C дешевле
  оказывается RDS Single-AZ с остановкой на ночь.
- **#664**: D -> **A**. Predictive scaling обучается на повторяющихся суточных и
  недельных паттернах, а всплеск дважды в месяц таким паттерном не является. Мгновенный
  рост CPU в 10 раз при низкой базовой нагрузке закрывают burstable-инстансы в режиме
  unlimited, а реагировать на нерегулярный всплеск нужно по факту запросов.
